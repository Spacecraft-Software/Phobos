Product Requirements Document

RustDoom — A Modern Rust Port of DOOM 1 with GPU-Accelerated Rendering

Document Version: 1.0
Date: 2026-07-23
Status: Draft
Product Name: RustDoom (working title)
Product Type: Open-source, cross-platform game engine / source port
Target Game: DOOM 1 / The Ultimate DOOM era IWADs, user-supplied assets
Primary Technology Stack: Rust, wgpu, Rust GPU / SPIR-V shaders, compute-driven rendering

Legal note: DOOM is a trademark of id Software / ZeniMax / Microsoft. RustDoom is a fan/community engine concept. It does not distribute proprietary game assets. Users must supply legally obtained IWADs such as DOOM1.WAD, DOOM.WAD, or compatible shareware/registered data.

1. Executive Summary

RustDoom is a modern Rust implementation of the original DOOM 1 engine, designed to faithfully run the classic game while taking advantage of modern GPU technologies through the Rust graphics ecosystem.

The product will prioritize:

  • Authentic DOOM 1 gameplay
  • Vanilla demo compatibility where feasible
  • Modern GPU rendering using wgpu
  • Rust-native shader development using Rust GPU / SPIR-V
  • Cross-platform support
  • Safe, maintainable, data-oriented engine architecture
  • Mod support via PWADs and later DeHackEd

The engine will not merely replicate the original software renderer. It will provide a hybrid rendering system:

  1. Classic Accuracy Mode — visually faithful to the original renderer.
  2. Enhanced GPU Mode — modern GPU-driven rendering, optional dynamic lighting, high refresh rates, post-processing, and optional ray-traced enhancements.

The goal is to create a technically modern DOOM 1 engine that feels like a natural Rust ecosystem showcase: safe, fast, portable, and GPU-forward.

2. Vision Statement

Build the most robust, modern, and developer-friendly Rust engine for playing DOOM 1, preserving the original game’s behavior while using contemporary GPU techniques to enable high-performance rendering, modding, and future extensibility.

RustDoom should be suitable for:

  • Playing classic DOOM 1 on modern systems.
  • Learning engine programming in Rust.
  • Demonstrating modern Rust GPU technologies.
  • Creating and running DOOM 1 mods.
  • Benchmarking Rust graphics and compute pipelines.

6. Product Principles

  1. Correctness before cleverness
    Preserve DOOM behavior where it affects gameplay.

  1. Determinism is sacred
    Game simulation must not depend on floating-point nondeterminism or platform-specific behavior.

  1. GPU acceleration should not break authenticity
    Modern features must be optional and separable from classic behavior.

  1. Rust safety should be meaningful
    Unsafe code should be isolated, justified, and audited.

  1. Mod support is a first-class concern
    The engine must not assume only the base IWAD.

  1. Performance should be measured continuously
    Benchmarks and demo tests are part of CI.

  1. The engine should be understandable
    Clear crate boundaries and documentation are required.

10. Technical Architecture

10.1 Proposed Crate Structure

rustdoom/

├── rustdoom-core/        # Math, fixed-point, RNG, common types

├── rustdoom-wad/         # WAD parsing, lump virtual filesystem

├── rustdoom-sim/         # Deterministic game simulation

├── rustdoom-render/      # wgpu renderer, shaders, GPU resources

├── rustdoom-audio/       # Sound and music playback

├── rustdoom-input/       # Keyboard/mouse/gamepad abstraction

├── rustdoom-ui/          # Menus, HUD, automap, console

├── rustdoom-app/         # Windowing, main loop, CLI, config

├── rustdoom-shaders/     # Rust GPU / WGSL shaders

└── rustdoom-tools/       # WAD inspection, demo testing, benchmarks

10.2 Core Design Principles

Deterministic Simulation

The simulation crate must be independent of rendering and input polling details.

  • Fixed timestep: 35 Hz.
  • Fixed-point arithmetic for gameplay-critical values.
  • Integer RNG.
  • Input represented as TicCmd structures.
  • No floating-point dependence in gameplay logic.

Renderer Independence

The renderer receives a read-only snapshot of the simulation state and produces visuals.

  • Interpolates between tics for high refresh rates.
  • Does not mutate gameplay state.
  • Can be replaced by software renderer or headless validator.

Asset Pipeline

WAD data is transformed into engine-native resources:

  • Textures packed into atlases or texture arrays.
  • Flats converted to GPU textures.
  • Sprites converted to instanced billboard resources.
  • Maps converted into renderable mesh batches.
  • Collision data retained for simulation.

11. GPU Rendering Strategy

11.1 Graphics API Choice

Primary API:

  • wgpu

Reasons:

  • Cross-platform.
  • Modern Rust-native GPU API.
  • Supports Vulkan, Metal, D3D12, OpenGL, and WebGPU.
  • Works well with Rust GPU and WGSL shaders.
  • Provides validation, compute shaders, and modern resource management.

11.2 Shader Strategy

Preferred: Rust GPU / SPIR-V

Use Rust GPU where practical to write shaders in Rust.

Benefits:

  • Shared CPU/GPU types.
  • Compile-time safety.
  • Better tooling.
  • Reduced duplication between simulation/render data structures.
  • Strong fit for a Rust-native engine.

Fallback: WGSL

WGSL shaders must be maintained as a fallback for:

  • Platforms where Rust GPU/SPIR-V is unavailable.
  • WebGPU targets.
  • Rapid shader prototyping.
  • Driver-specific debugging.

The shader abstraction should allow both paths to produce the same visual result.

11.3 Rendering Modes

Mode A: Classic Accuracy Mode

Purpose: preserve original DOOM visual feel.

Features:

  • Palette-based lighting.
  • Original colormap behavior.
  • Sector light levels.
  • Pixelated textures.
  • Optional original aspect ratio.
  • Sprite rendering faithful to original sorting/clipping.
  • Optional CRT/scanline filter.

Implementation:

  • GPU-accelerated but visually constrained.
  • Final output passes through palette LUT.
  • Texture filtering disabled by default.
  • Optional dithering.

Mode B: Enhanced GPU Mode

Purpose: use modern GPU capabilities while preserving DOOM’s art direction.

Features:

  • High-resolution rendering.
  • Optional anisotropic filtering.
  • Widescreen FOV.
  • Smooth sprite scaling.
  • Optional dynamic lights.
  • Optional ambient occlusion.
  • Optional ray-traced shadows/AO.
  • Optional upscaling.
  • Optional bloom and tone mapping.

Implementation:

  • Forward or clustered-forward renderer.
  • Compute-based light culling.
  • GPU-driven culling where practical.
  • Optional RT effects via wgpu ray tracing extensions where available.

14. Simulation Compatibility Requirements

14.1 Determinism

The engine must support deterministic playback by ensuring:

  • Fixed 35 Hz simulation.
  • Deterministic RNG.
  • Fixed-point arithmetic.
  • Stable iteration order.
  • No dependence on wall-clock time in simulation.
  • No dependence on renderer state.

14.2 Vanilla Behavior

The engine should reproduce:

  • Player movement physics.
  • Monster infighting.
  • Projectile collision.
  • Hitscan puffs.
  • Door/lift timing.
  • Weapon switching behavior.
  • Ammo consumption.
  • Damage calculation.
  • Respawn behavior.
  • Fast monster behavior.
  • Nightmare skill behavior.

20. Legal and Licensing Requirements

20.1 Asset Policy

  • The engine must not ship proprietary DOOM assets.
  • The engine may support freely redistributable shareware DOOM1.WAD if legally permitted.
  • Users must provide their own IWADs for full registered/Ultimate DOOM.

20.2 Engine License

Recommended options:

Option A: GPL-2.0-or-later

Use if the implementation is derived from or heavily informed by the official DOOM source release.

Advantages:

  • Compatible with DOOM source lineage.
  • Clear for source port community.

Option B: Apache-2.0 OR MIT

Use only if the implementation is clean-room and not derived from GPL source.

Advantages:

  • More permissive.
  • Easier integration with Rust ecosystem.

The project must choose one license before public release and document it clearly.

20.3 Trademark

  • Do not imply official endorsement.
  • Use clear naming such as “RustDoom is a community engine compatible with DOOM 1 data files.”
  • Avoid using DOOM logos or official art without permission.

30. Recommended Technical Decisions

30.1 Use wgpu

Recommended. It is the most practical modern Rust GPU abstraction and supports the broadest set of target backends.

30.2 Use Rust GPU Where Practical

Recommended, but not as the sole shader path. Maintain WGSL fallback for portability.

30.3 Keep Simulation CPU-Based and Deterministic

Required. GPU should accelerate rendering, not gameplay logic.

30.4 Provide Two Rendering Modes

Recommended:

  • Classic Accuracy Mode for preservation.
  • Enhanced GPU Mode for modern systems.

30.5 Avoid Full Boom/ZDoom Compatibility in v1

Required to keep scope achievable.

34. Final Recommendation

RustDoom should be built as a deterministic Rust simulation core with a modern wgpu-based GPU renderer, using Rust GPU shaders where practical and WGSL as a portable fallback.

The product should not attempt to become a full ZDoom-like port in version 1.0. Instead, it should focus on:

  1. Running DOOM 1 correctly.
  2. Providing a modern GPU rendering pipeline.
  3. Demonstrating the strengths of Rust for game engines.
  4. Supporting mods and preservation features.
  5. Remaining maintainable, safe, and cross-platform.

If executed well, RustDoom can be both a playable classic DOOM engine and a strong technical showcase for modern Rust GPU technologies.
