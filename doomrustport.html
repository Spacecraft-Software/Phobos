1 Overview ¶

A memory-safe Rust port of Doom 1, Doom II, and Ultimate Doom: one codebase, one WAD-selectable engine, no C left in the tree. id Tech 1 is the classic systems-porting benchmark — a tight, well-studied ~55,000-line C engine (45k .c + 9.5k headers in linuxdoom-1.10) with a software renderer, fixed-point math, and a fully deterministic game loop — which makes it the ideal proving ground for Rust’s safety guarantees under real-time constraints. No existing Rust effort has shipped a complete, faithful port of all three IWADs; that gap is the opportunity.

2 Source Material ¶

id Software released the Doom source on 1997-12-23 as linuxdoom-1.10 — the Linux port, because the DOS version’s licensed DMX sound library could not be published; the sound code was replaced. John Carmack authorized GPL relicensing on 1999-10-03, and GPL-2.0 was formally applied to the canonical id-Software/DOOM repository in January 2024. Note that Bernd Kreimeier’s pre-release cleanup introduced a few bugs (later fixed in Doom Classic), so vanilla-fidelity work should diff against known corrections. Doom II and Ultimate Doom run on the same engine; supporting all three is a matter of IWAD detection, episode logic, and Doom II’s cast/finale screens.

3 Prior Art ¶

Three Rust efforts define the landscape; none is complete.

room4doom

(MIT) The furthest along: playable, demo-compatible with vanilla Doom, software renderer plus an optional 3D mode, OPL2 music emulation. Hand-transliterated from the C, organized as per-system crates. Still missing the Doom II cast sequence, automap, and some audio effects; development is sporadic.

iron-doom

(GPL-3.0) A Chocolate-Doom-based rewrite on Bevy’s ECS. Early stage (~12 commits) and largely inactive — an architecture experiment, not a port.

rust-doom

(Apache-2.0, ~2.4k stars) cristicbz’s renderer built from the Doom specs rather than the C source. No gameplay; inactive. Useful as a reference for idiomatic WAD/BSP handling in Rust.

4 Porting Strategies ¶

1. Shim first, rewrite inward

doomgeneric (GPL-2.0) reduces the platform surface to six functions: DG_Init, DG_DrawFrame, DG_SleepMs, DG_GetTicksMs, DG_GetKey, DG_SetWindowTitle. Wrap them in Rust, get a running game on day one, then replace C subsystems incrementally. Fastest to playable; slowest to 100% Rust.

2. Mechanical transpile, then refactor

c2rust emits working-but-unsafe Rust from the C tree; the port then becomes a measurable campaign of driving the unsafe count to zero, module by module. Verifiable at every step, but the intermediate code is not idiomatic.

3. Manual transliteration

The room4doom route: rewrite the C by hand, preserving game-logic structure (and thus demo compatibility) while making the renderer, I/O, and platform layers idiomatic Rust from the start. Highest effort, cleanest result — and the one that showcases memory-safe design rather than inheriting C’s shape.

5 Constraints and Ecosystem ¶

Determinism is the fidelity contract: demo playback requires bit-exact 16.16 fixed-point arithmetic and the original 256-entry P_Random table — no f32 in game logic. The engine’s pervasive global mutable state is the central Rust design problem; plan ownership boundaries (a top-level game-state struct passed by &mut, or per-system crates) before writing code. Licensing: the GPL covers only the code — DOOM.WAD and DOOM2.WAD remain commercial, so develop and CI against Freedoom’s free IWADs and the shareware doom1.wad. Ecosystem: winit + pixels/softbuffer (or SDL2 bindings) for video, rodio/cpal for audio keep the stack memory-safe end to end.
